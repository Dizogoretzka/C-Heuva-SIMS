# As-Built System Specification

## C. Heuva Junior Secondary School Information System

| Document detail | Value |
|---|---|
| Version | 3.0 |
| Date | 21 October 2026 |
| Status | Describes the implemented application |
| Intended audience | Administrators, teachers, school stakeholders, developers, and testers |

## 1. Purpose

This document describes the current behavior of the C. Heuva Junior Secondary School Information System (SIMS). It replaces earlier descriptions that no longer match the implemented application. It covers the administrator, teacher, and learner roles, their interfaces, access restrictions, and the current reporting and attendance features.

## 2. System overview

SIMS is a browser-based Django application for managing school learner and academic records. It provides username, password, and PIN sign-in; role-specific registration; profiles; learner and subject management; results and grades; attendance; communications; login activity; and downloadable PDF reports.

The application uses the database and media storage configured by the deployment. Email is not used for sign-in, account registration, or password recovery. Registration codes and optional browser push depend on deployment configuration and external services.

## 3. Current features

### 3.1 Landing, sign-in, and registration

- The landing page offers Administrator, Teacher, and Learner sign-in choices.
- Each role has a role-specific sign-in page. Users provide a username, password, and five-digit PIN; a valid account cannot sign in through another role's page. Failures use a generic message, and configured account and IP lockout limits apply. Legacy accounts without a username can temporarily use their email in the username field while `SIMS_ALLOW_EMAIL_SIGNIN` is enabled.
- Learners can register when at least one course/grade exists. They select a grade; their session/term is left unassigned until an administrator assigns it.
- Administrator registration requires the configured `ADMIN_REGISTRATION_CODE`.
- Teacher registration requires the separate configured `TEACHER_REGISTRATION_CODE`.
- Registration collects first name, last name, username, gender, password, password confirmation, and an optional profile picture. Learners also select a grade. Registration codes are required for administrator and teacher accounts. Email is not collected.
- Usernames are 4-20 characters, start with a letter or digit, use only letters, digits, dots, underscores, and hyphens, and are unique across roles without regard to case. The retained email field is optional and non-unique. Password confirmation and Django password validators are enforced. Profile pictures are optional JPG, JPEG, or PNG images up to 5 MB. Account and profile creation is transactional.
- After registration, a one-time PIN is shown on a no-cache confirmation page; the user is redirected to sign in and is not signed in automatically. Repeated registration attempts from an IP address are rate-limited. Sign-in pages direct people who forget their password or PIN to ask a teacher or administrator.

### 3.2 Administrator interface

Administrators can:

- View the administrative dashboard, learner and subject totals, and recent learner sign-in information.
- Add, list, edit, and delete learner accounts. Edit learner details and assign or change course/grade and session/term.
- Add, list, edit, and delete teacher accounts. Set a teacher's password when creating an account or set a replacement password when editing one.
- Add, list, edit, and delete subjects.
- View learner login activity, including learner name, username, course/grade, login date/time, and IP address. Filter by learner name or username, date, and course/grade; browse paginated results.
- Review and approve or reject learner leave requests.
- View learner feedback and send replies.
- Send in-application notifications to learners. Browser push delivery is optional and depends on Firebase and client configuration.
- View and update their own first name, last name, and profile picture; username is read-only. Administrator passwords and PINs cannot be changed through a web page, including Django Admin. The system operator sets them with the management commands.
- Set replacement passwords or PINs for learner and teacher accounts. Administrators can reset either role; teachers can reset learners only. The password/PIN is shown once on a no-cache confirmation page, and resetting credentials clears lockout counters without changing the other credential.
- Generate the school-summary and class-list PDF reports.
- View recorded attendance in a read-only attendance records page. Administrators cannot take or edit attendance.
- Maintain course/grade and session/term records using Django Admin; the main administrator interface does not have dedicated course or session management pages.

Administrators cannot manage learner results or grade bands, generate learner-results or attendance-summary reports, or generate report cards. Those academic functions belong to teachers.

### 3.3 Teacher interface

Teachers use the administrator-style page layout and styling with a role-specific dashboard and navigation. Teachers can:

- View a dashboard showing learner and subject totals.
- View and update their own first name, last name, profile picture, and password; username is read-only. A password change requires the current password and keeps the teacher signed in. Teachers can request a new PIN from their profile by confirming their current password and PIN.
- Set replacement passwords or PINs for learner accounts. Teachers cannot reset teacher or administrator credentials.
- List, add, edit, and delete learner accounts using the existing learner forms and rules, including assigning a course/grade and session/term when editing.
- View the subject list without adding, editing, or deleting subjects.
- Create, update, and delete learner results with test/continuous-assessment and examination scores.
- Create, edit, and delete grade bands. The minimum score cannot exceed the maximum, and score ranges cannot overlap. Gaps are shown as warnings but do not prevent saving.
- Generate learner report cards for a selected learner and session/term.
- Generate class-list, learner-results, and attendance-summary PDF reports. Results and attendance reports can be filtered by subject where available.
- Take attendance for a selected course/grade, subject, session/term, and date. Load previously entered attendance for correction. Saving updates an existing matching attendance record instead of creating a duplicate.

Teachers cannot manage teacher accounts or subjects, review leave requests, reply to feedback, send learner notifications, access learner login activity, view the school-summary report, or open administrator attendance records.

### 3.4 Learner interface

Learners can:

- View their dashboard, subjects assigned to their course/grade, and subjects not assigned to a specific grade.
- View only their own results. Each displayed total is the test score plus the examination score; the grade is calculated from the current grade bands.
- Download a report card only for themselves, when results exist for their assigned session/term.
- View only their own attendance records and calculated attendance percentage.
- View notifications addressed to them.
- Submit leave requests and view their status.
- Submit feedback and view administrator replies.
- View and update their own first name, last name, profile picture, and password; username, course/grade, and session/term are read-only on their own profile. A password change requires the current password and keeps the learner signed in. Learners can request a new PIN from their profile by confirming their current password and PIN.

Learners cannot access administrator or teacher pages or see other learners' results, report cards, or attendance.

### 3.5 System operator

The system operator configures the deployment, database, media storage, environment secrets, Django Admin access, and optional Firebase services. The operator assigns usernames and issues initial PINs using `create_usernames <csv_path>` and `issue_pins <csv_path>`, then securely distributes and deletes the one-time CSVs. Set `SIMS_ALLOW_EMAIL_SIGNIN=False` after usernames have been handed out. The operator sets administrator passwords and PINs with `set_admin_password <username>` and `reset_admin_pin <username>`. This is an operational responsibility rather than a fourth SIMS application role.

## 4. Users and permissions

| Role | Current access |
|---|---|
| Visitor | Landing page, role-specific sign-in and registration pages. Forgotten passwords or PINs must be reset by authorized school staff or the operator. |
| Administrator | Learner and teacher accounts, subjects, school summary and class-list reports, learner communications and leave review, learner login activity, and read-only attendance records. |
| Teacher | Shared learner management and read-only subjects; results, grade bands, report cards, class/results/attendance reports, and taking attendance. |
| Learner | Own subjects, results, report card, attendance, notifications, leave requests, feedback, and restricted profile. |
| System operator | Deployment and authorized Django Admin maintenance; not a separate application role. |

An account has one application role and a globally unique username, compared without regard to case. The optional email field is retained for legacy data only; no email service is required. Role separation is enforced on the server, not only by navigation links. Unauthenticated visitors are redirected away from protected pages. The selected role at sign-in must match the authenticated account's role.

## 5. Data and business rules

1. `CustomUser` stores a case-insensitively unique username, optional non-unique email retained for legacy accounts, password hash, gender, profile image, a five-digit PIN hash and issuance time, and one of the administrator, teacher, or learner role values. Each role has its corresponding one-to-one profile.
2. A username has 4-20 characters, starts with a letter or digit, and contains only letters, digits, dots, underscores, and hyphens. The username may remain empty only during legacy-account migration; `create_usernames` assigns a unique username to each account that lacks one.
3. Learner course/grade and session/term assignments may be empty. Public learner registration assigns a grade and leaves the session/term unassigned.
4. A subject may be assigned to a course/grade or be available to all grades. Teachers can view subjects but only administrators can change them.
5. A learner result stores test/continuous-assessment and examination scores. The displayed total is their sum. The application does not define a universal maximum score.
6. Grade bands are created and maintained by teachers; the application does not create default bands. Grade symbols are calculated at display time using inclusive minimum and maximum boundaries. Results outside configured bands display "Not graded." Existing results reflect subsequent grade-band changes without being rewritten.
7. An attendance record identifies a course/grade, subject, session/term, and date. Its per-learner records store present or absent. Re-entering the same course, subject, session/term, and date loads and updates the existing record. A unique database constraint prevents duplicate attendance sessions for that selection.
8. A learner's attendance percentage is the number of that learner's present records divided by their marked attendance records. Learners see only records associated with their own profile.
9. Learner login activity is recorded only after successful learner sign-in. Administrator and teacher sign-ins and failed sign-ins do not create learner login-activity records.
10. Password and PIN reset actions clear failed-attempt counters and active locks while preserving the other credential. Self-service profile changes require the current password; self-service PIN changes also require the current PIN.
11. Leave requests, feedback, replies, notifications, results, and attendance entries are associated with learner profiles. Deleting related accounts follows configured database relationships.
12. Results use the learner's currently assigned session/term; a result does not contain a separate session/term field.

## 6. Reports

- **School summary PDF (administrator):** learner, course/grade, and subject counts.
- **Class-list PDF (administrator or teacher):** learners matching the selected course/grade and session/term.
- **Learner-results PDF (teacher):** learner results for the selected course/grade and session/term, optionally filtered by subject.
- **Attendance-summary PDF (teacher):** present and absent counts and attendance percentage for learners in the selected course/grade and session/term, optionally filtered by subject.
- **Learner report-card PDF (teacher):** one learner's results for a selected session/term, with subject scores, total, calculated grade, band description and remark, overall average total, and blank class-teacher and principal remark lines.

Reports require the applicable course/grade, session/term, learner, or subject selections. If no matching data exists, the application displays a message rather than returning an empty PDF. Learners can download only their own report card.

### 7.2 SMTP and email services

SIMS does not send email and requires no SMTP host, credentials, or email settings. Password-reset email and email-based recovery links are not provided. The optional email column is retained only to preserve existing account data and to support temporary sign-in for legacy accounts while `SIMS_ALLOW_EMAIL_SIGNIN=True`.

## 8. Features not currently provided

- Attendance recording is provided; a separate attendance-history migration may have removed records created by earlier versions. Records are not recoverable from the current schema unless they exist in an external backup.
- Dedicated main-interface pages for course/grade or session/term maintenance.
- Admissions, fees/payments, timetabling, examination scheduling, parent/guardian accounts, or a native mobile application.
- Guaranteed browser push delivery; this depends on configured external providers.
- Email-based password or PIN recovery, SMTP delivery, and email notifications are not implemented.
- Usernames and initial PINs must be distributed by authorized school staff using the one-time CSVs. Until usernames have been assigned, legacy email sign-in remains enabled when `SIMS_ALLOW_EMAIL_SIGNIN=True`.
- Default grade bands, a universal score maximum, or automatic validation that all result totals fit a school-wide score range.
- Guaranteed service availability, performance targets, backup/restore procedures, or data-retention schedules.

### Known limitations

- Existing accounts must receive usernames and initial PINs from the operator-generated CSV files. The school is responsible for distributing those values securely and removing the CSV copies.
- Temporary email sign-in is available only for accounts without a username and only while `SIMS_ALLOW_EMAIL_SIGNIN=True`; it must be disabled after username distribution.
- The application has no email-based password/PIN recovery. Forgotten learner and teacher credentials require an authorized teacher or administrator; administrator credentials require the operator.
- The system does not enforce a universal maximum result score or require grade bands to cover every possible total.

## 9. Operational and security notes

- Set `ADMIN_REGISTRATION_CODE` and `TEACHER_REGISTRATION_CODE` securely in the deployment environment. Do not put either code in source control.
- Run `create_usernames <csv_path>` and `issue_pins <csv_path>` for existing accounts; distribute each CSV securely and delete all copies. Set `SIMS_ALLOW_EMAIL_SIGNIN=False` after username distribution.
- Use `set_admin_password <username>` and `reset_admin_pin <username>` for administrator credentials. There is no administrator credential-reset web page.
- Passwords are stored using Django's password-hashing mechanism and validated with configured Django password validators.
- Production deployments must provide secrets outside source control, use HTTPS, configure allowed hosts and persistent database/media storage, and restrict database, Django Admin, and backup access.
- The application handles learner personal data. The school/operator is responsible for determining applicable privacy, consent, retention, and backup practices.

### School-staff credential reset note

When a learner forgets a password or PIN, an administrator or teacher can open that learner's account and choose **Set password / Reset PIN**. Administrators can do this for learners and teachers; teachers can do it for learners only. A replacement password or generated PIN is shown once after saving, so staff should give it directly to the account holder and avoid recording or sharing it in an unsecured channel. Resetting one credential clears the lockout but leaves the other credential unchanged. Forgotten administrator credentials must be reset by the system operator with `set_admin_password <username>` or `reset_admin_pin <username>`.

## 10. Acceptance criteria

1. The landing page offers administrator, teacher, and learner sign-in. Each role's login accepts a username, password, and PIN only for accounts assigned to that role; sign-in failures use a generic message and configured lockout rules.
2. Each role can register without email. Username validation, case-insensitive uniqueness, role-specific registration codes, password/image validation, and one-time PIN confirmation work as specified. Legacy email sign-in can be disabled after usernames are distributed.
3. Administrators can manage learner and teacher accounts and subjects, reset learner/teacher credentials, review leave and feedback, send notifications, view learner login activity, view attendance records, and generate school-summary and class-list reports.
4. Teachers can manage learners, view subjects read-only, manage results and grade bands, generate report cards and class/results/attendance reports, take or correct attendance, reset learner credentials, and update their own profile.
5. Administrators cannot access teacher-only results, grade-band, report-card, results-report, or attendance-taking functions. Teachers cannot access administrator-only teacher management, subject editing, leave/feedback/notification, login-activity, school-summary, or attendance-record pages.
6. Learners can access only their own results, report card, attendance, notifications, leave requests, feedback, and restricted profile. Teachers/learners cannot set administrator credentials, and administrator credentials cannot be changed through any web page, including Django Admin.
7. Users can change their own password with the current password; teachers and learners can request a new PIN with their current password and PIN. Staff credential resets clear locks and preserve the other credential.
8. Attendance saves present/absent status for the selected class and date, updates an existing matching session rather than creating a duplicate, and displays an individual's attendance percentage to that learner.
9. Reports return PDFs for matching records and display a no-data message when there are no matching records. Login activity and account reports display usernames rather than email addresses.
10. Production deployment configures secrets, HTTPS, database/media storage, and optional Firebase services separately from source code. SMTP is not required or used.

## 11. Traceability

This as-built specification reflects the Django models, forms, routes, views, role middleware, templates, migrations, and automated tests in `main_app/` and deployment settings in `student_management_system/settings.py`.
